Building the API Golden Path at LEGO Scale

A platform engineering approach to help 250+ product squads build, document, and find APIs — without the platform team becoming a bottleneck.

The Real Problem: Fragmentation Overload

Our distributed product squads face operational bottlenecks that slow down feature delivery:

Discovery Friction (51% Struggle)

Engineers cannot locate existing cross-domain endpoints, leading to duplicate builds and fragmented architectures.

Documentation Gaps (67% Frustrated)

API definitions are frequently stale, lack standardised schemas, or remain hidden inside private repositories.

The 38% Duplication Waste — a Real Example

At Maersk, working on a high-volume logistics platform, I watched eight separate squads independently build the same domain-event validation middleware. When we audited post-incident, we found over 10,000 lines of near-identical code spread across the codebase.

A searchable API catalog would have surfaced the first version in minutes. The other seven squads would never have built it.

We cannot fix this through mandates — we must earn adoption by making the platform the easiest path.

Key Assumptions — Stated Upfront

The case invites explicit assumptions. These four shape every design decision that follows.

Backstage Is Already Running

The case states a developer portal based on Backstage already exists. I am extending adoption of what the team has already deployed — not introducing new infrastructure. The platform team has existing operational knowledge of it.

Demo Scoped to OpenAPI / REST

The case asks for 2–4 hours of effort and a lightweight prototype. I chose REST as the most prevalent protocol. The CLI architecture is pluggable — AsyncAPI for Kafka and graphql-inspector for GraphQL follow the identical validate → emit → register flow. The demo proves the pattern; the drivers are a sprint extension.

Champion Pool Already Exists

The developer survey shows 67% would value better discoverability and 58% are already aware of the platform. I am not building a champion network from zero — I am connecting engineers who already care to tooling that makes them successful.

GitHub Actions as CI Standard

I assume GitHub is the primary code-hosting platform, enabling the CI gate pattern shown in the demo. For teams on GitLab or Azure DevOps, the same validation steps translate directly — different runner syntax, identical logic.

What I have not assumed: that any squad will adopt this because we built it. Every design choice — local CLI, CI gate, Backstage templates — is optimised to earn adoption, not mandate it.

The Philosophy: Make the Right Thing Easy

Enforcing rigid governance creates friction. Developers route around platforms that slow them down — keeping adoption stuck at 35%.

1. Self-Service First

Provide value at the engineer's workstation: instant linting, visual mocks, and automated scaffolding. No ticket needed.

2. Fast Feedback

Replace slow manual review boards with deterministic linting integrated directly into CI/CD. Errors caught in seconds, not days.

3. Visibility as Incentive

Make high-quality APIs visible through maturity scores — giving teams a concrete reason to care about their design quality.

From experience: At Boyum IT, we encoded Clean Architecture conventions into a .instructions.md file that GitHub Copilot reads as context. Adoption hit 100% within the sprint — not because we mandated it, but because it made developers measurably faster and cut code review back-and-forth by ~30%. Same principle: build tools engineers actually want to use.

Not Just REST: Kafka, GraphQL, and More

To scale across 250 autonomous squads, the validation layer must support the protocols teams actually use — without creating new barriers.

Pluggable Validator Architecture

The local CLI loads the right linter based on the repo configuration:

  • REST: Spectral parses openapi.yaml.
  • Event Streams: AsyncAPI driver validates Kafka schemas.
  • GraphQL: graphql-inspector catches breaking schema changes.

Team-Level Customisation

Product squads extend the central ruleset with local rules — adding domain-specific checks without forking the platform or waiting for the core team.

CI as Safety Net: No Manual Review Boards

The local CLI helps developers iterate quickly. The CI gate is the final automated check before code reaches main — no human in the loop.

What the Gate Does

  • PR checks: Every pull request automatically runs the full validation ruleset.
  • Hard gate: Builds fail if contract errors are present — broken specs cannot reach production branches.
  • Drift detection: CI alerts if runtime behaviour starts to diverge from the declared API schema.

How Drift Detection Works

A team adds a new response field to an API (e.g., discount_code) but forgets to update the OpenAPI spec. The CI monitor catches this mismatch within the hour and alerts the team: "Your spec says [id, customer_id, total_amount, status] but production is returning [id, customer_id, total_amount, status, discount_code]." The team either updates the spec or reverts the code. Downstream consumers never experience surprise breaking changes.

Backstage: Templates, Catalog, Dependency Graph

We use Backstage as the portal layer — an interconnected service graph, not a static API list.

Software Templates

New services spin up via Backstage templates that include standard CI config, default linting rules, and the validation CLI pre-wired — the Golden Path is the default path.

Dependency Graph

Backstage tracks which squads consume which endpoints — giving the platform team full visibility into cross-domain dependencies and blast radius of any breaking change.

Honest note: I haven't operated Backstage in production yet — my familiarity is through architecture research and hands-on work with the catalog and template concepts. I'd treat month 1 as a structured onboarding sprint: pairing with whoever on the team knows it best before making architectural decisions.

How 8 Engineers Support 2,000 Developers

A small core platform team cannot hand-hold every squad. The model is about leverage, not headcount:

Tier 1: Self-Service (80%)

Automated hooks and Backstage templates guide developers through setup with zero hands-on support from the platform team.

Tier 2: InnerSource (15%)

An internal champion network builds and contributes custom validation plugins back to the platform — the team scales through the community, not headcount.

Tier 3: Advisory (5%)

Core team involvement reserved for critical migrations and complex domain designs where the stakes are highest.

Future Direction: Smarter API Search

Keyword search breaks when teams use different names for the same concept — searching "payment" misses an endpoint called /v1/charges. Longer-term, semantic search would help teams find existing APIs even when terminology differs.

How It Would Work

  • Schema Extraction: Read OpenAPI description fields during catalog ingestion.
  • Vectorisation: Generate text embeddings from endpoint descriptions.
  • Semantic Store: Index vectors for intent-based querying.

Phased Approach

Start with what Backstage already provides before investing in vector infrastructure:

Months 1–3: Backstage metadata search.
Months 4–6: Spike to measure indexing cost vs. accuracy delta.
Months 7–12: Decision point — invest or defer based on spike results.

Future Direction: AI-Aware Platform

As squads increasingly use AI coding assistants, the platform can expose structured API context to those tools — making suggestions more accurate without requiring engineers to paste specs manually. Interesting direction; not a day-one deliverable.

Migrating the Other 65%: Low Friction, Phased

We cannot rewrite 780 legacy APIs overnight. The strategy meets teams where they are and reduces friction at every step:

  • Phase 1 — Discover and Document (Month 1–2): Background repo scanners find shadow endpoints and build a low-touch baseline inventory.
  • Phase 2 — Light Ingestion (Month 3–5): Accept partial specs with basic owner tags — register services without requiring full compliance rewrites up front.
  • Phase 3 — Golden Path Alignment (Month 6–12): Automated scaffolding tools help legacy squads upgrade their specs at their own pace.

First 90 Days: Discovery, Tooling, Early Wins

Focusing on foundational reliability in the first 90 days establishes the base everything else builds on.

Month 1: Discovery

Deploy background repo scanners. Build the initial catalog in Backstage. Identify the 15 highest-value shadow APIs to prioritise first.

Month 2: Tooling

Ship the local validation CLI. Run a spike to evaluate whether semantic search adds enough value to justify the infrastructure investment.

Month 3: First Wins

Roll out the GitHub Actions validation gate. Onboard the first champion cohort. Publish adoption metrics to the wider team.

Month 4–12: Champions, Self-Service, 80% Target

Once the automated loops are running, focus shifts to scaling adoption across the wider engineering organisation.

  • InnerSource Expansion (Month 4–6): Train decentralised champions to build custom linting plugins and grow rule coverage without central team involvement.
  • Self-Service Scale (Month 7–9): Scale onboarding flows to target 180 registered squads. Track adoption weekly, remove friction wherever drop-off occurs.
  • 80% Target (Month 10–12): Complete legacy migrations to bring 80% of organisation APIs under active management. Publish a year-one retrospective.

What Could Go Wrong and How We Prevent It

Platform tools only work if developers use them. Anticipating friction is part of the design.

Risk: Validation Slows Builds

Developers bypass tools that add noticeable latency to their workflow.

Mitigation: Keep local validation sub-second — non-negotiable design constraint. Provide auto-fix suggestions so failures don't become blockers.

Risk: Support Overload

An 8-person team can be overwhelmed by tickets from 2,000 engineers during a rollout.

Mitigation: Error messages that explain the fix, not just the failure. Use the Tier 2 champion network to handle first-line questions before they reach the core team.

Risk: Adoption Stalls Without Visible Early Wins

Teams hear about the platform but don't see value for their own work, so they avoid it.

Mitigation: Identify 15 teams in pain (the 51% struggling with discovery) in Month 1. Make them successful and visible. Word spreads when peers see a team solve their problem. Adoption follows credibility, not mandates.

Risk: Backstage Operational Overhead

A new platform to operate could become a bottleneck if the core team gets pulled into constant maintenance.

Mitigation: Treat Month 1 as a structured onboarding sprint with the existing Baseplate team. Clarify on-call procedures and runbooks up front. The platform should be self-healing wherever possible — if a validation rule breaks, revert it automatically and alert the author.
